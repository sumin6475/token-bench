## 가설 A — 로컬 24~35B급으로 잘 될 것

- 요약, 번역, 문체 교정, 리라이팅, 분류/추출
- 일상 코딩 보조 — 함수 짜기, 버그 설명, 코드 리뷰, 정규식/SQL
- 브레인스토밍, 초안 잡기, Q&A, 문서 기반 답변(RAG)
- 프라이버시 필요한 작업 (데이터가 기기 밖으로 안 나감)

## 가설 B — 로컬로 약하거나 안 될 것 (당분간 클라우드)

- 길고 자율적인 에이전트 작업 (여러 단계 tool use로 오래 자율 실행) — 로컬의
  tool-calling이 약점. Claude Code 완전 대체는 어려움
- 최전선 추론 — 어려운 수학/알고리즘, 복잡한 다단계 논리
- 아주 긴 컨텍스트 (큰 코드베이스 통째로)
- 속도가 생명인 것 (대량 배치, 즉답 UI)

한 줄: **일상의 8할은 로컬 대체 가능, 2할(긴 에이전트·최고난도 추론)은 아직 클라우드.**

## 하드웨어 가설 (결정 맥락)

- "70B 되나?"의 답은 **용량(GB)**, "70B 쓸 만하나?"의 답은 **메모리 대역폭**.
- Mac mini 진입선: **M4 Pro + 48GB(하한) / 64GB(권장)**. 기본 M4는 대역폭 절반이라 처짐.
- 단, 64GB여도 70B는 대역폭 병목으로 느림 → **실사용 만족은 24~35B급**이 중론.
- PC/게이밍 랩탑은 시스템 RAM이 아니라 **GPU VRAM**이 상한 (8GB→~8B, 16GB→~32B).

## 갱신 (2026-08-23) — 측정 축을 task 라벨에서 컨텍스트-핏으로 재설계

원래 검증 방법은 대시보드의 **By task type** 표에서 task별 peak ctx를 보는 것이었다.
와이어를 직접 읽어보니 이 축이 세 가지 이유로 망가져 있었다:

1. **세션이 여러 task를 넘나든다** → 세션 단위 라벨은 의미가 약하다.
2. 로컬 가능성을 결정하는 세 변수 중 **컨텍스트 크기만 깨끗하게 측정된다.**
   - tool-use 의존도: Claude Code OTel `api_request`에 tool 필드가 **없다.**
   - 추론 난이도: thinking이 `output_tokens`에 섞여 **분리 불가.**
3. peak ctx(세션 최대값 1개)보다 **요청별 컨텍스트 분포**가 훨씬 많은 걸 말해준다.

그래서 축을 **요청 단위 컨텍스트-핏 분포**(객관적, 라벨 불필요)로 바꿨다.
task 라벨은 삭제 대신 접힌 보조 렌즈로 강등.

### Stage 0 결과 — prompt.id 가설: **성립**

"Claude Code가 한 턴의 tool 루프 안 여러 api_request에 같은 `prompt.id`를
재사용한다"는 가설을 실제 앱 DB로 확인. 성립했다 —
`COUNT(*) GROUP BY prompt_id`로 한 프롬프트가 **최대 39회 왕복**한 게 잡혔고,
그 1개 프롬프트가 그 기간 비용의 약 45%였다. 그래서 이걸 "프롬프트당 왕복 수 =
agentic-intensity **대리지표**(정답 아님)"로 대시보드에 넣었다. Claude Code 전용
(프록시는 prompt_id가 null이라 제외).

### 새 검증 방법 (2주 뒤 여기서)

1. 대시보드(⌘D) → **Context fit** 히어로 차트(30일).
2. 두 막대를 본다: 요청의 몇 %가 각 컨텍스트 밴드에 있나 vs. 비용의 몇 %가 있나.
   - `≤32K → 8B · ≤128K → 24~35B · ≤200K → 대형 로컬 · >200K → 프론티어/클라우드`.
3. **Token anatomy**로 토큰 구성(캐시 읽기 비중)을, **Agentic intensity**로
   깊은 tool 루프가 비용에서 차지하는 비중을 본다.
4. 결론은 "task가 로컬 가나"가 아니라 **"내 요청 중 몇 %가 로컬 윈도우에 담기고,
   비용은 어디에 몰리나"** 로 답한다. (담긴다 ≠ 잘 된다는 여전히 별개 — 품질은 미측정.)

### 초기 실측 (재베이스라인 전 스냅샷, 참고용)

깨끗한 2주 창을 위해 DB를 재베이스라인하기 전, 기존 데이터에서 이미 나온 그림:

- 요청의 다수가 **128K 이상** 컨텍스트, 비용의 ~88%가 **128K–1M** 밴드에 몰림
  → 흔한 24~35B(32K~128K) 로컬 윈도우로는 상당 부분이 **안 담긴다.**
- 전체 input 토큰의 **~97.7%가 cache read** — 비용 이야기는 fresh input이 아니라
  캐시다 (PRD 목표 #2가 몸으로 확인됨).
